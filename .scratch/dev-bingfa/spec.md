# 規格：AI 系統開發兵法（`dev-bingfa`）1.0

定案日期：2026-11-24。來源：使用者與 Claude 的四輪問答（Q1–Q20），使用者已逐題確認。
本文件是開工依據。內容與使用者的新指示衝突時，以使用者為準，並回頭更新本文件。

## 1. 目標

做出一個可以發給公司同事的包裹，把一套固定的 AI 開發流程裝進他們的 AI 工具，**照說明書就能開始用**。

導入理由：開發者和 AI 工具都會變多（已用 Claude Code，將導入 Codex）。有了固定流程，只要目標寫得明確，不論誰做、用哪個工具，品質都能保持穩定。

## 2. 使用者

- **第一批使用者**：公司同事。程度假設為**不會寫程式**。
- **維護人**：本專案擁有者（使用者本人）。同事的問題與建議都回報給他。
- 不公開發布。

| 既有專案探勘 | `~/.claude/skills/brownfield-recon` | 要改：不再自己記專有名詞，只產出專案地圖（見第 5 節） |

- 任何個人資料、金鑰、對話紀錄。

## 4. 支援的工具（兩級制）

| 級別 | 工具 | 內容 | 驗證 |
|---|---|---|---|
| 完整版 | Claude Code、Codex | skill＋助手設定＋檢查腳本＋規則 | 必須實測 |
| 基本版 | Cursor、Antigravity 等 | 只有 skill 和通用規則 | 無法實測，說明書標明「未實測」 |

基本版使用者拿不到「獨立審查由另一個 AI 做」和「存檔時自動攔錯」的自動化，說明書要寫出手動替代做法。
包裹結構要預留位置，之後為某個工具補做完整版時不必重來。

## 5. 規則上的統一

1. **主線只用 Matt 的流程**：追問需求 → 寫規格 → 切任務卡 → 先測試再實作 → 獨立審查 → 交付與檢討。原規則第 6 節的流程說明照此改寫。
2. **名詞只記在 `GLOSSARY.md`**。探勘工具不再維護自己的名詞區；原規則裡「以 `CONTEXT_MAP.md` 的 Language 節為準」的說法一併移除。
3. **規則拆三份**：
   - 通用規則：所有工具都用。一份內容、兩個檔名（Claude Code 讀 `CLAUDE.md`，Codex、Cursor、Antigravity 讀 `AGENTS.md`）。
   - Claude 專用附錄：只給 Claude Code。
   - 個人偏好範例：回覆語言、驗收方式、模型名稱等，讓同事自己改。
4. **規劃與實作分工只留原則**（大範圍閱讀與實作交給助手，主對話負責規劃與審查）。具體模型名稱移到個人偏好範例。
5. **任務卡預設放專案資料夾裡的本地檔案**。說明書註明已在用 GitHub Issues 的團隊可以改選。

## 6. 說明書

繁體中文，寫給不會寫程式的人：每一步都是「複製這行、貼上、看到什麼畫面代表成功」。共三份：

1. **安裝**：依工具分章。Matt 工具先走官方安裝；連不上外部網路就改用離線副本。
2. **第一次使用**：跟著做一個小任務，走完整條主線。
3. **日常速查**：一頁流程圖、每個步驟打什麼指令、卡住時怎麼辦。

封面主標「AI 系統開發兵法」，副標「固定開發流程包」。

## 7. 發放與版本

- 公司共用資料夾放壓縮檔，檔名帶版本號，從 1.0 開始。
- 旁邊放一份更新紀錄：每版改了什麼、要不要重裝。
- 舊版保留不刪，新版有問題可以退回。
- 直接出正式版 1.0（使用者的決定；已知這套流程尚未經真實任務試跑，問題靠改版修正）。

## 8. 發出去之前的三關

三關都過才發。每一關要留下使用者看得懂的證據（畫面、前後對照、可以自己重做的步驟）。

1. 在乾淨環境照說明書一步步實裝 Claude Code 版和 Codex 版（本機已有 `codex-cli 0.140.0`、Node v24、Python 3.12、Git）。
2. 裝完後實際跑一個小任務，走完主線。
3. 請一位同事在他自己的電腦上照說明書實裝；卡住的地方改進說明書。

## 9. 限制

- **不得修改** `~/.claude` 下的任何東西。使用者的電腦維持原始版，不換成包裹版。後果：使用者與同事的環境有差異，重現同事的問題要在乾淨環境另裝一次。
- 不得讀取 `~/.claude/projects/`、`.credentials.json`、歷史紀錄、`todos/`、`shell-snapshots/` 或任何憑證檔。
- 不使用 `git add -A` 或 `git add .`。不推送、不建立遠端。
- 提交一律經由 `/commit` 或 `implementer` 助手。
- 包裹內容發出前要檢查沒有個人資料與金鑰。

## 10. 已查到的事實

來源是 2026-11-24 兩位助手讀官方文件的回報；動手前請對照原文再確認一次。

- Matt 的工具官方支援 Claude Code、Codex、Copilot、Gemini CLI，其他工具用 `npx skills@latest add mattpocock/skills -a <工具>`（需要 Node 22.20 以上）。
- Claude Code：自己的 skill、助手、指令、檢查腳本可以包成「外掛」（`.claude-plugin/plugin.json`），可從本地資料夾安裝，不需要 GitHub。外掛裡的助手設定有幾個欄位會被忽略（`permissionMode`、`hooks`、`mcpServers`、`initialPrompt`）。
- Claude Code 的外掛**不能**附帶或修改使用者的 `CLAUDE.md`，只能在說明書教人手動貼上。
- Codex：原生支援 skill（`.agents/skills`、`~/.agents/skills`），規則檔是 `AGENTS.md`，助手設定是 TOML 格式（要轉寫），檢查腳本機制的事件種類與 Claude Code 不同。
- Cursor：讀 `.agents/skills/`、`.cursor/skills/`，也會讀 Claude Code 的 skill 與助手資料夾；讀 `AGENTS.md`。
- Antigravity：專案層讀 `.agents/skills/` 與 `AGENTS.md`。

## 11. 還沒驗證的事（開工後要先解決）

- Codex 的外掛包裝格式，以及同一包能不能讓 Claude Code 與 Codex 共用。
- 同事的電腦能不能連 GitHub（使用者的電腦可以）。
- Antigravity 的資訊只來自搜尋摘要，官方頁面當時連不上；它「整台電腦」層級的 skill 路徑有三種互相矛盾的說法，所以說明書只教裝在專案資料夾。
- Cursor 的文件沒有明說 `AGENTS.md` 是否每次對話都自動帶入。
- `patent-argument-writing` 等被排除的工具是否被留下的工具引用（需檢查留下的三個 skill 與助手設定有沒有懸空引用）。
- 「AI 系統開發兵法」有沒有同名的書或產品：中文搜尋涵蓋很弱，只能說沒找到。
